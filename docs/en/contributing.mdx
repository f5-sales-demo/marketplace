Add a plugin with a canonical manifest and a concise documentation page, then
verify it through the repository's contribution workflow.

## Prerequisites

- A current source checkout and the required tools for the changed plugin.
- A detailed issue with objective acceptance criteria.
- The repository's [contribution rules](https://github.com/f5-sales-demo/marketplace/blob/main/CONTRIBUTING.md)
  and [style guide](https://github.com/f5-sales-demo/marketplace/blob/main/STYLE_GUIDE.md).

Allow about 15 minutes to register and document a plugin after implementation.
Plugin development and live acceptance depend on its runtime.

## Register the plugin

1. Create `plugins/<PLUGIN_IDENTIFIER>/` with a stable identifier.
2. Define identity, catalog metadata, and lifecycle in `.xcsh-plugin/plugin.json`.
3. Add focused skills, commands, agents, or native extensions as required.
4. Declare runtime prerequisites, dependencies, setup, and collection fields.
5. Generate `.xcsh-plugin/marketplace.json` from the plugin manifests:

   ```bash
   node scripts/generate-marketplace-catalog.mjs
   ```

Use the [manifest reference](/marketplace/en/reference/) and an existing plugin
with the same lifecycle as examples. Keep large references separate from skill
instructions. Inspect managed-file ownership before changing fleet scaffolding.

## Write the plugin page

Add one primary page under `docs/en/plugins/` and link it from the catalog.
Preserve existing published routes when updating a page.

Use the same `Badge` components for category and lifecycle. Let the shared
Starlight theme control typography, color, spacing, and navigation. Keep current
version numbers in manifests and releases so page badges don't drift.

Use these sections in order:

- Prerequisites
- Set up
- Use the plugin
- Verify
- Clean up
- Related resources

Lead with the task outcome. Use sentence-case headings, active voice, short
paragraphs, and one action per numbered step. Use tables for task comparisons
and descriptive links for shared setup and complete command definitions.
Document actual registered names and link claims to implementation sources.

These conventions follow Microsoft's
[style and voice guidance](https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice)
and [heading guidance](https://learn.microsoft.com/en-us/style-guide/scannable-content/headings).
Develop English documentation under the repository's translation policy.

## Verify

```bash
node scripts/generate-marketplace-catalog.mjs --check
bash scripts/validate-plugins.sh
bash scripts/lint-mdx-prose.sh docs/en/plugins/*.mdx
```

Run the plugin's appropriate tests and installed acceptance. Build the site and
check changed pages, navigation, and links. Confirm that every manifest entry
has one primary catalog link and that commands match packaged definitions.

## Submit the change

Use a fresh issue-numbered branch and worktree from fetched `origin/main`.
Open a completed pull request with `Closes #<ISSUE_NUMBER>` and validation
evidence. Follow required checks and branch repair through merge; for docs
changes, verify the merged Pages deployment.

## Clean up

Inspect tracked and ignored files before retiring the task worktree. Remove
only confirmed-merged local branches and disposable verification output.
Preserve unrelated work and any private runtime material still required.
