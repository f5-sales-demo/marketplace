Inspect Google Cloud accounts, projects, compute instances, and storage buckets.

<Badge text="Cloud" variant="tip" /> <Badge text="Integrated" variant="note" />

## Requirements

- Google Cloud CLI, `gcloud`.
- An authenticated account and the intended active configuration and project.

## Install

```bash
xcsh plugin install gcloud@f5-sales-demo-marketplace
```

Check readiness and complete [integration setup](/marketplace/en/getting-started/#complete-setup) if required.

## Inspect the active project

Use `gcloud_config_list` to confirm the active account, configuration, and project. Ask `gcloud_compute_instances_list` or `gcloud_storage_buckets_list` for that project, then compare returned resources with the requested scope.

| Task | Native tool |
| --- | --- |
| Inspect active configuration | `gcloud_config_list` |
| List projects | `gcloud_projects_list` |
| List compute instances | `gcloud_compute_instances_list` |
| List storage buckets | `gcloud_storage_buckets_list` |
| Inspect command usage or execute an explicit command | `gcloud_help`, `gcloud_exec` |

If credentials expire, repeat human setup and reconfirm the active project before continuing.

## Optional command groups

For commands or help paths beginning with `alpha` or `beta`, the plugin checks
the installed SDK components and automatically installs the missing group with
noninteractive arguments. It coordinates installation across callers and verifies
the group before executing the requested command. Child CLI prompts are disabled.
Existing cloud write and credential guards still apply.

If the component manager is disabled by the SDK's package installation, or the
group cannot be verified after installation, the tool returns recovery guidance
for that installation's supported package manager. It does not launch the cloud
command after a failed preparation.

## Customer Edge readiness

Use the `gcp-ce` skill for GCP Customer Edge planning and inspection.
`gcp_project_identity` verifies an explicit project, `gcp_compute_discover`
observes F5 image/license identities and cloud prerequisites, and `gcp_ce_plan`
validates topology and sizing with a hashed readiness plan. Native is the default;
an explicit Terraform choice must match the intent.

The plan contains no executable actions. Immutable API v12.1.3 includes GCP
schema and observational mappings with both-engine single-node boot evidence.
Public deployment, upgrade and failover remain unavailable
pending full integration. Their tools report these gaps before mutation.
Inventory, status and diagnostics observe cloud provisioning; registration,
physical interface identity, platform health, routing and application traffic
remain separate unknown gates. Deployment labels alone cannot authorize deletion.

For the qualified single-node `n2-standard-8` profile with SLO and SLI interfaces,
readiness plans collect live IAM, quota, effective policy, zone and image/license
checks. They retain sanitized source hashes and reject stale evidence or a changed
intent. Capacity reservation and verified Marketplace acceptance remain explicit;
passing cloud prerequisites alone does not enable deployment.

`gcp_marketplace_agreement` qualifies the pinned image's agreement and can accept
an exact reviewed document programmatically. Supply the versioned intent, review
the returned plan and use its `approvedPlanHash`. Existing consent references are
discovered from Google; an absent or ambiguous mapping requires an exact agreement
and document reference for server validation. Optional `enableMarketplaceApi=true`
requests scoped API enablement. The tool checks active consent after granting and
reconciles interrupted grants without duplicate acceptance. It places no orders.

### Google Cloud terms prerequisite

Google may require acceptance of its prerequisite Cloud terms before enabling
the Consumer Procurement API. The tool reports `cloud_terms_not_accepted`, the
provider code `UREQ_TOS_NOT_ACCEPTED`, an acceptance link and recovery steps.

1. Open [Google Cloud terms](https://console.developers.google.com/terms/cloud).
2. Sign in with the same Google account used by `gcloud`.
3. Review and accept the terms shown, selecting the intended project if prompted.
4. Retry scoped API enablement and agreement qualification to verify recovery.

No supported API for this prerequisite acceptance has been qualified. These
terms are separate from the F5 Marketplace agreement; verify current F5 consent
afterward. Successful live Marketplace acceptance remains unqualified.

For an existing disposable native single-node deployment, `gcp_ce_teardown`
prepares an exact saved review from its persisted intent and ownership ledger.
Supply the explicit project, region, deployment name and F5 context. After review,
use `gcp_ce_apply` with `operation=teardown` and that plan's `approvedPlanHash`.
The profile requires two interfaces, external IP egress, no ingress and no
destination routes. It rechecks all six cloud identities and the owned XC
site/token binding before deleting, preserves authorization across interruption,
and verifies fresh absence. Installed qualification covers synthetic Compute
resources and live XC cleanup; installed live GCP cloud teardown remains pending.

An explicit Terraform engine uses the candidate owning-engine teardown path.
It requires stored session inputs and original Platform identities recorded after
the exact creation plan completed. The destroy review projects named nonsensitive
state fields and rechecks live cloud, site and token identity. It applies only
the reviewed saved binary, preserves authorization across interruption and
requires an empty current destroy plan plus independent absence. A partial lost
apply remains pending until its outcome is independently reconciled.

Installed Terraform qualification verified Platform identity capture, a no-change
follow-up plan, exact owned site/token destroy and independent absence without
creating a GCP VM or network. Full installed live cloud teardown remains pending.
Older deployments without the required original ledgers cannot be silently adopted.

For an existing ledger-owned deployment, status and diagnostics with explicit
region and its persisted `platformContext` use shared Platform observations.
They correlate registration and physical interfaces against exact VM identities
and report matching-node global health. HA health, routing, application traffic
and independent absence remain unqualified.

Disposable native and shared Terraform runner qualification also observed matching
node global health after initial software and OS convergence, followed by owned
cleanup and independent absence checks. These campaign results do not establish
HA, routing, application traffic, explicit upgrades or 120-second recovery.
