Use the xcsh manifests and validation scripts as the source of truth for
plugin identity, packaging, and lifecycle behavior.

## Source files

| Source | Purpose |
| --- | --- |
| `.xcsh-plugin/marketplace.json` | Generated plugin catalog and current versions |
| `plugins/<PLUGIN_IDENTIFIER>/.xcsh-plugin/plugin.json` | Canonical identity, catalog metadata, and lifecycle |
| `scripts/generate-marketplace-catalog.mjs` | Generates catalog entries from plugin manifests |
| `scripts/validate-plugins.sh` | Validates manifests and packaged components |
| `scripts/check-version-bumps.sh` | Enforces versions for changed plugin content |

These are repository paths. See the
[catalog generator](https://github.com/f5-sales-demo/marketplace/blob/main/scripts/generate-marketplace-catalog.mjs)
and [manifest validator](https://github.com/f5-sales-demo/marketplace/blob/main/scripts/validate-plugins.sh)
for the enforced fields.

## Manifest fields

| Field | Purpose |
| --- | --- |
| `name`, `version`, `description` | Plugin identifier, semantic version, and purpose |
| `marketplace.order` | Catalog ordering |
| `marketplace.catalog.source` | Plugin directory relative to the repository root |
| `marketplace.catalog.category` | Discovery category |
| `lifecycle.mode` | `content`, `on_demand`, or `integrated` |
| `lifecycle.integrations` | Registered integration identifiers |
| `lifecycle.requirements` | Human-readable prerequisites |
| `lifecycle.setupRequired` | Whether the plugin declares setup |
| `lifecycle.setupAuthorization` | Whether reviewed direct installation may authorize bounded setup |
| `lifecycle.pluginDependencies` | Required marketplace plugins |
| `lifecycle.collectedData` | Profile data categories collected by setup |
| `extensions`, `xcsh` | Native extension entry points and presentation metadata, where declared |

The generator copies identity and catalog metadata from each plugin manifest.
Edit those inputs, then regenerate the catalog. Content plugins cannot declare
integration setup.

## Plugin layout

```text
plugins/<PLUGIN_IDENTIFIER>/
  .xcsh-plugin/
    plugin.json
  skills/
    <SKILL_NAME>/SKILL.md
  commands/
    <COMMAND_NAME>.md
  agents/
    <AGENT_NAME>.md
  extensions/ or src/
    <NATIVE_ENTRY_POINT>
```

Components beyond the manifest depend on the plugin. A command file's basename
and plugin identifier form its namespaced slash command. Extensions can also
register commands, such as `/zoom`, and typed tools. Link to the actual source
rather than predicting a command from a skill name.

## Readiness and setup

```bash
xcsh plugin status <PLUGIN_IDENTIFIER> --json
xcsh plugin status <PLUGIN_IDENTIFIER> --context <CONTEXT_NAME>
```

Status returns an `integrations` array for enabled integrations. A configured
CLI or account can be ready while a requested cloud or desktop operation still
fails its own checks. Inspect the operation's verification evidence as well.

Human setup requires an interactive terminal and reviews the selected plan.
Platform's context wizard runs through `/plugin setup platform` inside xcsh.
See [Get started](/marketplace/en/getting-started/) for the shared lifecycle.

## Validate a source checkout

```bash
node scripts/generate-marketplace-catalog.mjs --check
bash scripts/validate-plugins.sh
bash scripts/lint-mdx-prose.sh docs/en/plugins/*.mdx
```

Run these from the repository root. The first command checks generated catalog
convergence; the others validate packaging and English Markdown with JSX (MDX)
prose. Installation acceptance also requires a fresh session using the released
plugin, followed by its documented verification steps.

## Other plugin hosts

xcsh packaging doesn't establish OpenAI or Claude Code compatibility. OpenAI
supports portable Agent Plugins and documented compatibility manifests, with
its own marketplace configuration. See
[OpenAI plugin packaging](https://developers.openai.com/plugins/build/plugins)
when targeting ChatGPT or Codex. Verify the host's supported package and runtime
before describing a cross-client installation workflow.
